## 2. Observed Submission Target (hosted form)

- `<form id="application-form" enctype="multipart/form-data" method="POST">`
  — **no `action` attribute** → the browser submits to the **current URL**
  (the apply page itself: `https://jobs.lever.co/{site}/{postingId}/apply`).
- Job identity lives in the URL path (postingId). Company/account identity:
  hidden `accountId` input (per-account UUID) + the URL site segment.
- Encoding: `multipart/form-data`. Native browser submit (after hCaptcha
  token) — evidence: the inline script calls `formSubmitButton.click()` on
  the hidden submit button, i.e. a **standard HTML form POST**, not XHR.
- Confidence: HIGH (4 sampled boards identical).

### Official API (separate path — NOT candidate-usable)

- `POST https://api.lever.co/v0/postings/SITE/POSTING-ID?key=APIKEY`
  (JSON or multipart; resumes only in multipart). The `key` is generated by a
  **Super Admin of the EMPLOYER account** — a candidate cannot obtain it.
  Modeled on the hosted form; field names match the hosted form.
- Success: `200 OK` + `{ok:true, applicationId:'...'}` (OFFICIAL).
- Error: `{ok:false, error:<string>}` (OFFICIAL).
- Rate limit: 2 application POSTs/second → `429` (OFFICIAL).
- Dedupe: **candidates are de-duped by email address** (OFFICIAL).
- The hosted form remains the only candidate-side submission path.

## 3. Serialization Contract (observed + official mirror)

### Standard fields (hosted form input names == official API fields)

| Field | HTML | Required | Submission representation |
|---|---|---|---|
| Full name | `name="name"` | required (attr) | `name=<value>` |
| Email | `name="email"` | required (attr + pattern) | `email=<value>` |
| Phone | `name="phone"` | required on sampled boards | `phone=<value>` |
| Current location | `name="location"` + hidden `selectedLocation` | optional (Veo) | `location=<text>`, `selectedLocation=` (autocomplete token, may be empty) |
| Current company | `name="org"` | optional | `org=<value>` |
| LinkedIn/GitHub/Portfolio/Other | `name="urls[LinkedIn]"` etc. | optional | `urls[LinkedIn]=<url>` (bracketed multipart key, official) |
| Resume | `name="resume"` `type="file"` | required on sampled boards | multipart file part; 100MB client-side cap text on Veo |
| Timezone | hidden `timezone`, value set by inline JS (`Intl.DateTimeFormat`) | transport | `timezone=<IANA>` (official: silently ignores invalid) |

### Custom questions (cards)

- Rendered inputs: `name="cards[{cardId}][field{N}]"`.
- Types map to native inputs:
  - `multiple-select` → checkbox group, **same name repeated** (multipart
    repeats the key per checked box), value = option TEXT ("Yes"/"No").
  - `multiple-choice` → radio group, single value = option TEXT.
  - `dropdown` → `<select>` with `<option value="<text>">`.
  - `text` / `textarea` → plain value.
- Observed submitted values are the **option display texts**, NOT the
  `optionId`s present in the baseTemplate JSON. Evidence: rendered input
  `value` attributes equal option `text`; the baseTemplate optionIds never
  appear in rendered markup. Confidence: HIGH for hosted form; UNKNOWN
  whether server maps text→id server-side (it must, since text is sent).
- The `cards[{cardId}][baseTemplate]` hidden input is the question schema
  (entity-encoded JSON): fields array with type/text/required/id/options.
  It is replayed as-is by the browser (it is a hidden input).

### Hidden / transport metadata (hosted form)

| Name | Class |
|---|---|
| `accountId` (per-account UUID) | REQUIRED_TRANSPORT_METADATA (stable per employer) |
| `timezone` | REQUIRED_TRANSPORT_METADATA (client-computed; stable per user) |
| `cards[...][baseTemplate]` | REQUIRED_TRANSPORT_METADATA (question schema) |
| `resumeStorageId` | OPTIONAL_TRANSPORT_METADATA (empty on static GET; populated by resume parse flow — UNKNOWN semantics) |
| `origin`, `referer`, `source`, `socialReferralKey`, `socialSource` | TRACKING (optional; browser may send some) |
| `linkedInData` | OPTIONAL (AWLI integration payload; empty) |
| `selectedLocation` | OPTIONAL_TRANSPORT_METADATA |
| `h-captcha-response` | REQUIRED when board uses hCaptcha (see §6) |

Stability: `accountId`/baseTemplate stable per job; `timezone` stable per
user; `origin`/`referer`/`source` vary per request (volatile, tracking).

### Consent

- Observed: `consent[marketing]` — hidden `value="0"` + checkbox `value="1"`
  (standard unchecked→0/checked→1 pattern). This is a **marketing opt-in**
  ("contact me about future job opportunities"), NOT legal consent. The
  `data-qa="consent-section"` container on sampled boards contains the
  marketing opt-in + privacy link.
- Official multipart syntax: `consent[marketing]=true` and
  `consent[marketing][provided]=true&consent[marketing][compliancePolicyId]=<guid>`
  (waved rollout mid-2024; `consent.store` likewise).
- No legal-consent checkbox observed on sampled boards. A legal
  consent/acknowledgement may exist on other boards (UNKNOWN; parser
  classifies it as CONSENT and execution must treat it per §10).
- **Never auto-accept.** Any consent checkbox requires explicit approval
  bound to the exact legal text (see ConsentApproval).

### EEO

- No EEO/demographic fields observed on any sampled board (4/4 = 0 hits).
- Official API/ATS: applications carry `gender`, `disability`,
  `eeoSurveyRespondedAt`; Lever's EEO API is anonymous/PII-isolated.
- EEO on hosted forms: employer-configurable, UNKNOWN presence.
- Policy: only explicit user selection; never inferred; optional unanswered
  → omit; required → MANUAL_ACTION_REQUIRED.

## 4. CSRF / Cookies / Challenge

- **CSRF**: no `csrf`/`authenticity_token`/nonce observed in form or page
  source. Status: NOT OBSERVED. (Absence of a token ≠ proof none is needed;
  same-site cookie checks are invisible in static HTML.) UNKNOWN.
- **Cookies**: cookieconsent banner JS (GA/Segment cookies), Cloudflare
  challenge-platform script injected (`/cdn-cgi/challenge-platform/...`).
  Cloudflare is in front of jobs.lever.co. Functional session cookies may be
  set (UNKNOWN without replaying; we do not persist any).
- **hCaptcha (major finding)**: ALL four sampled boards embed
  `js.hcaptcha.com` with the **same sitekey**
  (`e33f87f8-88ec-4e1a-9a13-df9bbb1d8120` — Lever-central hCaptcha account).
  The inline submit flow:
  `btn-submit click → hcaptcha.execute() → onSuccess(token) → token into
  hidden h-captcha-response → native form submit`.
  A board with hCaptcha cannot be submitted by a direct HTTP client without
  a valid token → **MANUAL_ACTION_REQUIRED** for those boards.
- **Cloudflare challenge**: observed on rapid repeat GETs (200 challenge
  page, no form). Classified PROVIDER_CHALLENGE (Phase 2A calibration).
  POST-side challenge behavior UNKNOWN; conservative: challenge anywhere →
  MANUAL_ACTION_REQUIRED, never bypass.

## 5. Success / Failure Semantics

### Official API (OFFICIAL_DOCUMENTATION)

- Success: `200 OK`, body `{ok:true, applicationId:'...'}` —
  **provider-positive proof exists: applicationId**.
- Error: non-200 + `{ok:false, error:<string>}`.
- 429 = rate limited (2 POSTs/sec).

### Hosted form (UNKNOWN — we never POSTed)

- A browser redirect to a confirmation page or a success screen is plausible
  but UNVERIFIED. HTTP 200 must NOT be treated as success without positive
  evidence. Verification design (§9) therefore requires provider-specific
  positive proof; without it → SUCCESS_UNCONFIRMED.

## 6. Execution Architecture (Design)

### 6.1 Capability model

```
lever: READ_ONLY_INSPECTION_SUPPORTED → (this phase) EXECUTION_RESEARCHED
hCaptcha boards:  EXECUTION_BLOCKED → MANUAL_ACTION_REQUIRED
no-hCaptcha board: ASSISTED_SUBMISSION_SUPPORTED (Phase 2+, user-approved)
nothing is AUTO_SUBMISSION_SUPPORTED yet
```

### 6.2 State machine

```
PENDING_APPROVAL ──approve──► APPROVED ──prepare──► PREPARING ──post──► SUBMITTING ──verify──► SUBMITTED
      │                     │                │            │
      ▼                     ▼                ▼            ├─► SUCCESS_UNCONFIRMED (ambiguous)
   CANCELLED             FORM_CHANGED     FAILED(no bytes) └─► FAILED (confirmed rejection)
                        (reinspection)    │
                                          ├─► MANUAL_ACTION_REQUIRED (challenge/captcha/consent/EEO)
                                          └─► SUCCESS_UNCONFIRMED (connection lost mid-write)
```

Invariants:
- `SUCCESS_UNCONFIRMED → SUBMITTING` is FORBIDDEN (no auto-retry after
  ambiguity; user review only).
- `SUBMITTED → SUBMITTING` FORBIDDEN (terminal).
- Crash during `SUBMITTING` → recover to `SUCCESS_UNCONFIRMED` on restart
  (never FAILED, never resubmit) unless verification proves the result.

### 6.3 Execution identity & local idempotency

Identity key (frozen inputs):
`userId + provider + externalJobId + packageSnapshotHash + planFingerprint`

SQLite durable protection (Phase 1): a unique constraint on
`(user_id, provider, external_job_id, plan_fingerprint)` prevents a second
attempt row; an in-process per-attempt lock coalesces double-clicks; no
Redis. Local dedupe is mandatory regardless of Lever behavior (Lever dedupes
by email — OFFICIAL — but that is provider-side and not observable to us).

### 6.4 ApplicationAttempt (durable, Phase 1)

Immutable at creation: id, userId, planId, packageId, provider,
externalJobId, planFingerprint, packageSnapshotHash,
requirementsFingerprint, approvalId, startedAt.
Mutable lifecycle: status, transportAttemptCount (counter of actual POSTs
sent; ≥1 only after bytes on wire), verification, failure, finishedAt.

`executeOnce(attemptId, ...)` owned by the engine: engine holds the
idempotency lock, validates approval + integrity, then invokes the adapter's
mutation boundary exactly once. The adapter NEVER retries a POST itself.

### 6.5 Approval binding

```ts
interface ConsentApproval {
  fieldId: string;            // e.g. 'consent[marketing]'
  legalText: string;          // exact visible text + linked policy
  legalTextHash: string;      // sha256 of legalText
  approvedByUser: boolean;
  approvedAt: string;
}

interface ApplicationApproval {
  id: string;
  planId: string;
  planFingerprint: string;
  packageSnapshotHash: string;
  requirementsFingerprint: string;
  resumeArtifactHash: string;
  mappedFieldsHash: string;   // sha256 over mapped answers (providerFieldId:value)
  consents: ConsentApproval[];
  approvedAt: string;
}
```

- Any change to plan/package/requirements/resume/mapped answers invalidates
  the approval → user must approve again.
- Legal text hash: if the provider changes consent text, old approval is
  invalid (the form-change re-inspection detects the changed text).
- EEO answers: only explicit per-field user selections; never inferred.

### 6.6 Pre-submit reinspection (TOCTOU control)

Before ANY mutation: fresh read-only GET inspection (respecting the 4s
cooldown), compare `requirementsFingerprint` against the approved plan's:

- unchanged → proceed (refresh volatile transport context only)
- changed → `FORM_CHANGED` → new plan + new approval; DO NOT submit.

Semantic requirements vs volatile transport:
- Semantic (fields/types/options/required/consent text) → fingerprint;
  changes invalidate approval.
- Transport-only (accountId, timezone, origin, template blob identical) →
  refreshed silently; approval semantics unaffected.
- Challenge during reinspection → `MANUAL_ACTION_REQUIRED`; no POST.

### 6.7 ProviderExecutionContext (transient only)

Fresh inspection output: hidden metadata, tokens, cookie jar (memory only),
target URL. Rules: short-lived; never in plan JSON / package / preview /
long-term DB; never logged. The adapter serializes it into the payload.

### 6.8 Verification & receipt

```ts
interface SubmissionVerification {
  status: 'PROVIDER_CONFIRMED' | 'SUCCESS_UNCONFIRMED' | 'REJECTED';
  providerApplicationId?: string;   // e.g. {ok:true, applicationId}
  confirmationUrl?: string;
  confirmationMarker?: string;      // response fingerprint / marker text
  evidenceHash: string;             // sha256 of sanitized evidence
}
```

- `SUBMITTED` requires positive provider proof (official hosted-form proof
  shape UNKNOWN; official API shape `{ok:true, applicationId}` is the
  reference). Without proof → `SUCCESS_UNCONFIRMED`, never auto-retry.
- Receipt: attemptId, provider, externalJobId, company, title, packageId,
  planId, submittedAt, verification, resumeArtifactHash, answersFingerprint.
  No secrets, no raw response bodies (sanitized fingerprint/status/redirect
  host only).

### 6.9 Retry classification

| Failure | Class |
|---|---|
| inspection GET failure | SAFE_RETRY (read-only, cooldown-respecting) |
| pre-submit validation/reinspection | SAFE_RETRY (read-only) |
| any POST before bytes sent (construct-only error) | SAFE_RETRY (transport certainty HIGH) |
| POST fully/partially sent, response lost | NEVER_AUTO_RETRY → SUCCESS_UNCONFIRMED |
| POST timeout after request write | NEVER_AUTO_RETRY → SUCCESS_UNCONFIRMED (Node fetch does not reliably expose write state) |
| provider 429 | REQUIRES_REINSPECTION (fresh token) + user-triggered |
| provider 4xx (rejection) | NEVER_AUTO_RETRY → FAILED (CONFIRMED_REJECTION) |
| challenge / captcha / consent / EEO | MANUAL_ONLY |
| 5xx | NEVER_AUTO_RETRY (ambiguous) → SUCCESS_UNCONFIRMED or FAILED per evidence |

### 6.10 Security threat model (concrete → mitigation)

| Threat | Mitigation |
|---|---|
| Malicious ATS question text (prompt injection) | Labels/options are inert TEXT, never executed, never rendered as HTML; answers never derived from question text beyond deterministic aliases |
| Malicious hidden values / form-action injection | Execution target = the apply URL from the approved job + inspection; NO following of form `action` (none exists); POST destination fixed and allowlisted |
| Redirect injection after POST | Success redirects validated against jobs.lever.co / lever.co; never follow POST redirects to arbitrary hosts |
| SSRF / private IP | Reuse inspection SSRF boundary (allowlist + DNS + private-IP) for the mutation fetch |
| Oversized/malformed responses | Bounded streaming + size caps + content-type checks (reuse) |
| Duplicate submission | SQLite unique execution key + in-process lock + executeOnce |
| Replay / stale approval | Approval binds fingerprint hashes; pre-submit reinspection; attempt immutability |
| Tampered PDF artifact | Re-read + SHA-256 + size + MIME check immediately before upload; never regenerate |
| PII in logs | Log only attemptId/planId/provider/state/status/error class; never name/email/phone/answers/EEO/consent/cookies/tokens/multipart body |
| Cross-user execution | Attempt/plan/package all user-scoped; ownership checks before every step |
| Ambiguous timeout | SUCCESS_UNCONFIRMED, never auto-retry |
| Challenge | MANUAL_ACTION_REQUIRED, never bypass |

### 6.11 Direct HTTP vs browser verdict

Recommendation: **DIRECT_HTTP for boards without hCaptcha; MANUAL_ONLY for
hCaptcha boards.** Evidence: native multipart form contract is stable and
simple; official API mirrors it; no CSRF token observed; session needs look
minimal (cookies unverified); hCaptcha boards cannot be automated honestly.
Browser automation adds fragility without removing the hCaptcha barrier and
is not chosen. No anti-bot evasion anywhere.

## 7. Phase 1 Implementation Plan (next milestone)

1. `application_attempts` table (unique execution key, status, transport
   attempt count, verification, failure).
2. Approval model (ApplicationApproval + ConsentApproval + persistence,
   invalidation rules).
3. Execution state machine + transition validator (pure, tested).
4. Idempotency lock (in-process + SQLite unique constraint).
5. Pre-submit reinspection + requirements comparison (semantic vs transport).
6. Immutable payload builder + **dry-run multipart serialization** (build the
   exact multipart body locally, never send; assert determinism, field
   names, card keys, option text values, resume part, metadata).
7. Verification contract + receipt model.
8. API/UI: approval preview + Approve & Apply (Phase 1 shows preview and
   builds payload; NO live POST until Phase 2 explicit approved smoke).
9. Tests: state transitions, approval stale on any fingerprint change,
   double-click, concurrency, crash-during-SUBMITTING, no auto-retry,
   consent binding, EEO manual, resume hash mismatch, cross-user, challenge,
   reinspection, multipart determinism.

## 8. First Real Submission Test (Phase 2, later)

Requires: explicit user approval; a real job the user wants; final preview;
exact resume artifact; exact answers; consent review; no EEO inference; one
attempt; no automatic retry; full receipt. Candidate board: must be a
no-hCaptcha Lever board (none sampled yet — detection rule: form embeds
`h-captcha` → MANUAL_ACTION_REQUIRED). Until then execution stays
read-only/dry-run.
